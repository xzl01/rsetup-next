## 1. 范围与决策分级

本文区分已确认决策、工程建议与后续细化事项。未单独确认的组件、参数和接口不视为最终选型。本次设计与 [protocol_spec.md](../../protocol_spec.md) 同步修订传输边界、审批保活、双流探测和时间语义；只写设计，不修改代码、数据库或其他文件，不代表功能已经实现。

## 2. 总体架构

```text
浏览器 ── HTTP ──→ Rust 中控服务（单进程）
                    ├── 内嵌 Vue 3 页面与管理 API
                    ├── 用户、登录与授权
                    ├── 设备档案、分组与准入
                    ├── 查询调度与最新状态缓存
                    ├── 主任务／子任务调度
                    ├── 板端连接与会话
                    └── 审计
                         │
                         └── MySQL / TiDB

板端 ── 自定义安全隧道 ──→ 同一进程的独立设备协议端口
```

浏览器只访问中控，不直连板端。单进程不等于内嵌数据库；MySQL／TiDB 是独立依赖。

建议划分认证、授权、设备管理、接入会话、查询状态、任务、审计模块。接入模块负责握手、流路由和请求关联，不代替用户鉴权；任务模块执行编排，不把硬件执行搬进中控。

中控和板端分开运行，建议共享协议定义、业务消息与稳定标识。首版不引入微服务、分布式会话路由或跨进程消息队列。

## 3. 身份与首次初始化

### 3.1 用户管理

管理员负责用户、角色与授权；普通用户即使拥有全部设备操作权限，也不自动具有全局管理权。用户自行改密、管理员重置、停用和最后一个管理员保护的具体规则继续细化。

### 3.2 初始化流程

创建 `admin` 并将初始密码写启动日志；不采用固定默认密码。建议：

1. 连接数据库并完成必要的结构迁移。
2. 检查持久初始化标记，通过唯一约束防止重复初始化。
3. 安全随机生成密码，只将安全密码哈希存入数据库。
4. 在事务中创建管理员、设置初次改密标记和初始化完成标记。
5. 提交成功后，仅在本次初始化日志中输出密码。

正常重启、升级、重跑迁移或异常用户表变化不能静默覆盖密码。误启动多个进程也不能相互覆盖初始化结果；这不代表支持多实例部署。

结构迁移与账号初始化不能假定整体可回滚，需考虑 MySQL／TiDB 的 DDL 行为。

### 3.3 强制改密与恢复

后端限制初始管理员仅能访问必要身份信息、自身改密和退出。改密前禁止设备、任务、授权和实时订阅，不只依赖前端跳转。

建议拒绝与初始密码相同的新密码，改密后清除标记、撤销旧会话并重新登录。新密码不写日志。

初始密码日志是敏感数据，需限制读取、集中转发与保留范围。初次改密前，日志密码仍可用于接管账号。

提交成功但密码输出前崩溃存在恢复窗口。建议提供本机 CLI 重置入口，不通过重新初始化数据库找回密码；其授权、密码交付与审计规则尚需确认。

## 4. 授权模型

### 4.1 最终权限

用户最终获得“设备列表 + 每台设备上的有效权限集合”。角色、设备组只是配置和批量管理手段。

```text
授权 = 用户 + 权限来源（角色／直接权限点）+ 范围（全部设备／设备组／单设备）
```

对用户和目标设备，取所有主体匹配且范围覆盖目标的授权，把权限点取并集。无授权默认拒绝，不设显式拒绝。

角色与范围必须成对绑定，不能分别合并全部角色和全部范围再交叉扩展。

### 4.2 动态规则

- 角色权限变化动态影响引用它的授权。
- 设备组成员变化动态影响组授权。
- 设备可属于多组，移出一组不影响其他授权来源。
- 删除单设备授权不能抵消组或全部设备授权提供的相同权限。
- 全部设备范围自然覆盖新接入设备，无须复制授权记录。
- 授权、角色和组成员变更完全由管理员操作，并记录审计。

建议展示最终权限来源；缓存结果必须在相关变更后失效。

### 4.3 鉴权边界

设备列表只展示具有有效访问权限的设备。详情、操作、订阅和任务查看均由后端鉴权，隐藏按钮不是安全边界。

批量操作逐台检查，执行前按最新权限复查；撤权不保证撤回已下发操作。管理员具有全局管理和全设备管理能力，普通用户不能转授权。

权限点目录、操作权限是否隐含查看权限、历史任务可见性需要细化；错误和批次汇总不得泄露不可见设备信息。

## 5. 准入、连接与档案

以板端公钥维护协议规定的 `PENDING / APPROVED / REVOKED`。序列号、型号和 IP 是描述信息，不替代密码学身份。

批准仅允许业务连接，不自动分组。管理员随后分组或单独授权；已有全部设备范围授权的用户自然获得相应权限。

分别维护准入状态、当前连接状态和数据新鲜度。数据库中的上次在线不等于当前在线；中控重启后等设备重新建连和采集。采集失败不立即等同于掉线，异常断线检测受协议保活时间约束。

### 5.1 审批连接与资源边界

审批记录按板端公钥去重持久化，连接断开不删除。健康 PENDING 无总审批期限：协议 §4.1 以 `SERVER_PENDING`/`PENDING_PONG` 实现握手阶段往返检测，名义周期 5s、pong 期限 10s、板端接收静默期限 15s；这些只是失联检测，不是人工审批截止时间。协议版本调整为 `0x02`，旧版本不自动降级。

状态转换按公钥串行，人工等待与网络 I/O 在锁外；同公钥新连接替换旧挂起连接，异步回调必须检查代际。已保存的批准/吊销决定不会因 pong 丢失而回滚为 PENDING。

未认证连接、已验签挂起连接及新公钥记录分别设容量上限，全局及按来源限制连接速率。约千台部署应为健康挂起连接预留容量；新的超限身份不能无限入库，验签通过也不豁免配额。已接纳连接不为容纳新连接而按等待时长驱逐。

资源不足时，若已具备完整认证上下文，按协议回复可退避重试的 `SERVER_ERROR`；此前拒接/关闭连接，按网络失败退避。不能用 `APPROVAL_DENIED` 或 `REVOKED` 表示资源不足，否则会错误停止板端自动重连。资源拒绝与人工拒绝分别审计。

建议首版审批页面支持检索、分页和按明确公钥清单批量批准，展示身份指纹、连接状态和逐项结果；不按 IP/SN 自动信任，也不因列表刷新把新记录加入已确认批次。公钥预录入为后续可选能力，需另行确认。

吊销后的恢复严格遵循[协议 §7 第 4 条](../../protocol_spec.md)：**管理员重新授权 + 板端人工重置本地未授权状态**。中控单独重新批准不保证设备恢复自动连接，界面必须提示仍需板端操作，不提供误导性“一键恢复在线”。

### 5.2 中控时间来源与板端时钟

中控运行独立 NTP 客户端，负责校验本机墙钟并为板端时间比较提供参考；不自动调整中控或板端的 OS 时间，也不要求板端有 RTC/NTP 服务。

**启动与持续重试**：

- 每次启动开始 NTP 查询，以本机单调时钟计算 **最多 30s 的总预算**，包含 DNS、多个源及所有请求等待；取得有效样本可提前结束等待。使用异步等待，不阻塞运行时线程。
- NTP 启动关卡结束前不开放管理业务及设备接入，也不恢复执行任务；数据库初始化可以先进行。取得样本或 30s 到期后，在其他启动条件满足时进入 ready。30s 只限制 NTP 引入的等待，不承诺包括数据库迁移在内的总启动时间。
- 预算内没有有效响应时，立即以中控当时系统墙钟作为参考并标记 `system_fallback`；不能伪装为已经校准。NTP 后台无限期重试，不因持续离线退出服务。
- 后台失败重试建议默认 `1s, 2s, 4s, …`，上限 60s，含抖动的实际等待为 `min(60s, base + uniform[0,1s))`；每次请求也有有界等待。有效样本成功后重置失败计数，改为建议每 60s 定期复验，样本建议有效期 180s；这些参数是工程默认建议，可配置，不是用户指定的最终数值。
- 重试等待、样本年龄都用单调时钟。墙钟跳变立即使旧偏差估计失效并调度重采样，但仍受请求预算/限速约束，不能因反复跳变形成请求风暴。

**来源与质量**：源列表来自部署配置。只接受与请求及配置源匹配的响应，拒绝 LI=3（未同步）、stratum 不在 1..15、时间字段非法或往返质量不合格的样本。未认证 NTP 只是运维参考，不能宣称抵御主动篡改；NTS 是可选增强。

时间提供者输出中控原始墙钟 `system_wall`、估算参考时间 `estimated_reference`、偏差 `offset`、不确定度 `uncertainty`、样本单调年龄 `checked_age`、来源、时钟代际及质量状态：

| 状态 | 含义与参考时间 |
| --- | --- |
| `ntp_valid` | 样本有效，按样本 UTC 与本机单调经过时间估算参考时间，不要求更改 OS 墙钟 |
| `system_fallback` | 尚无有效样本或已因跳钟失效，参考为当前中控墙钟；无可信 NTP 偏差 |
| `stale` | 曾有样本但已过有效期，当前仍回退墙钟；旧偏差仅作过期诊断，不能继续声称已校准 |

来源切换可导致参考时间不连续，必须递增时钟代际并记录事件，不重写既有采样或审计时间。有限期内估算的不确定度也应随样本老化增加，不能把旧样本无限当作准确时钟。

**板端校验**：通过已认证通道查询板端接收/发送系统时刻及同次单调时刻、`boot_id`。中控记录发送和接收参考时刻，按四时间戳估算板端偏差和往返不确定度；跨时钟代际、查询期间回跳、启动标识变化或延迟过大的样本弃用并标 `unknown`。不能将两端单调时钟直接比较为绝对时间，也不能仅因板端与中控差值很大就丢弃一份可用于报告偏差的有效测量。NTP 不可用时只报告相对中控的偏差，不称为板端相对标准 UTC 的误差。

板端原始采样时间、中控接收时间和各自质量分别保存。`boot_id` 是启动代际标识，不是时钟，重启核实不依赖时间戳递增。运行期查询、保活、任务 TTL 和 freshness 使用单调时钟。

跨中控重启不能复用旧进程的 monotonic 截止值；任务持久化需要保留创建时参考时间、绝对截止、时间质量和时钟代际。恢复后若无法可信地计算剩余寿命，尚未下发任务暂停待核实或按有效期规则终止，不因系统回跳而延长寿命；已下发任务仍只核实结果，不自动重发。

## 6. 主任务与子任务

### 6.1 结构

```text
主任务：批量重启
├── 子任务 A／设备 A：检查 → 下发 → 跟踪 → 核实
├── 子任务 B／设备 B：检查 → 下发 → 跟踪 → 核实
└── 子任务 C／设备 C：检查 → 下发 → 跟踪 → 核实
```

主任务保存发起人、操作、目标清单并组织调度和汇总，不直接执行。每个去重目标一个子任务；单设备操作也用一个主任务加一个子任务。

组范围提交时展开固定，后续组变更不添加目标，但影响执行时权限。目标限于用户可见范围；已纳入目标若离线、不支持或执行前失权，保留子任务及原因，不静默减少数量。

### 6.2 调度与互斥

不同设备受限并发，子任务内部步骤串行。同设备重启跨主任务互斥，占用检查和获取原子完成；后来者以设备忙结束，不排队等待后续执行。

单个子任务失败不自动停止其他设备。主任务汇总排队、执行、成功、失败及结果未知；准确枚举和汇总规则由业务协议定稿。

建议取消只阻止未下发任务，不承诺撤回已接收操作。并发上限、等待重连是否占用槽位、有效期及未知结果后的再次操作规则尚需确定。

### 6.3 执行证据

执行前检查最新权限、在线、能力与互斥，并展示目标和风险。先持久化任务，再下发稳定子任务 ID 对应指令。

接收不等于成功，掉线不等于重启完成。核实结合板端任务记录、重启前后 `boot_id` 等证据；单纯上线或 `boot_id` 变化不能排除其他原因触发的重启。

板端需持久去重和任务查询能力，同一子任务重复请求不得重复触发重启。具体落盘与执行原子边界需定义，不承诺跨故障 exactly-once 执行。

业务主子任务 ID 独立于 `trace_id`，后者仅关联请求响应，不是持久任务身份。

### 6.4 中控恢复

| 恢复状态 | 行为 |
| --- | --- |
| 确认未下发 | 重查权限、在线、有效期和互斥，通过后执行 |
| 已确认接收 | 恢复查询核实，不再次触发重启 |
| 可能下发但无响应 | 查询板端记录，不当作未执行 |
| 证据不足 | 结果未知，不自动重试 |
| 已结束 | 保留结果，不重新执行 |

数据库事务重试不能附带重复设备指令。恢复时先恢复任务占用与不确定性状态，再接纳冲突操作；具体下发边界和占用恢复机制需单独设计。

## 7. 查询调度与通知

### 7.1 中控查询

不采用板端自主定时遥测。常规状态目标每台在线设备 10 秒一次，1024 台平均约 102.4 次查询／秒，不是每 10 秒瞬间查询全部设备。

建议限制发起速率和在途数，同设备仅一个在途常规查询。采用**轮询错峰与过载跳过**：过载或超时延后、跳过本轮，不集中补发积压轮次；集中重连也错峰。

静态信息和能力在建连后及需要时查询，不每轮完整重复。任务核实和交互请求优先，但为周期采集保留额度。

浏览器读取中控快照，不因多个页面而重复轮询板端。建议周期监控不创建业务主子任务。

### 7.2 关键事件

主要逻辑中控查询，完成或失败等关键事件由板端通知。通知降低延迟，查询补偿丢失和恢复，不能依赖通知必达。

建议先保存结果再通知；查询响应和通知共用幂等更新，重复事件不重复处理，迟到的执行中响应不能覆盖确认终态。

重连和中控恢复后查询未结束任务，不依赖无限通知积压。重启前只能通知接收或准备执行，不能提前宣布成功。

### 7.3 最新快照

首版不存完整历史采样。每个最新快照分别记录：板端原始采样墙钟、采样时的 `boot_id`/单调序号、中控接收的参考时间及原始墙钟、来源与质量、有效偏差估计（如有）。不能覆盖原始板端值并把估算时间冒充原始采样时间。

页面默认按中控接收时间展示“最近收到”，板端时间仅在质量信息旁显示；发现板端回跳或未校准时明确标注，未知偏差不填 0。新鲜度由当前中控进程的单调接收时刻计算，快照顺序按当前会话/采样序号而非墙钟大小判断，旧会话结果不得覆盖新快照。中控重启后无快照则显示等待采集，不能用假零值或旧正常状态填充。

页面更新按当前权限过滤；具体质量阈值、采样序号消息格式和订阅撤权机制仍需细化。

### 7.4 双向流探测与业务边界

两条流按[协议 §6.7](../../protocol_spec.md) 各自进行应用级 `tunnel.ping` 请求/响应校验：同 action、同 `trace_id`、同流与当前代际，载荷为原始 16B nonce，pong 必须原样回显。双端都主动探测，有业务也不省略；首版 `OpenData` 无业务时不发空业务占位包，但仍建流并保活。

健康运行后，每端每流采用 15s 窗口与 15s probe 期限，连续 3 个窗口无有效 pong 则重开该流；probe 专用期限不套用普通请求的 5s。每方向/每流一个在途，计时包含入队和写阻塞。probe 与业务共用每端、每设备连接最多 1024 个未决项的预算，预留该连接两条流的探测名额；中控另设跨设备全局在途和内存上限，不按理论容量预分配。不承诺越过 FIFO 或避免底层阻塞。

HTTP/2 PING/ACK 只检查连接，应用 handler 解码分发后产生的 pong 才检查该流处理链路；后者仍不证明业务 worker、硬件采集或重启完成。普通业务请求需检查状态码、载荷与能力约束，任务需独立的执行结果证据。

流级故障不自动使另一流失败；板端负责重开，中控通过 `RST_STREAM` 触发。初次开流/重开的建立与首个 probe 校验各有 15s 期限；连续 3 次未健康重建才升级连接故障，不以 RPC 打开成功重置失败数。连接级失败合并清理，不启动重复重连循环。所有计时使用单调时钟。

若页面采用候选 SSE 方案，它是单向推送，不属于板端双流 Ping/Pong；浏览器重连与数据新鲜度另行处理。

### 8.1 备份、恢复与冷启动

DB、中控长期身份私钥和运行配置分别做安全备份，记录可组合恢复的版本和备份时间点；板端私钥留在板端，不集中备份到中控。明文初始密码日志不属于必要备份集。需验证 MySQL／TiDB 各自支持的备份与恢复方式，并通过恢复演练确认数据、身份和配置相互匹配。

从旧备份恢复不同于正常进程重启：可能丢失最近任务、吊销和密码变更。恢复后先进入管理员受控恢复阶段，暂停设备自动准入及变更任务调度，撤销旧登录会话，核对身份密钥、授权/吊销记录和板端任务记录，之后再开放。无法补齐的撤权或执行历史应明确标为未知，不能静默复活旧授权、旧密码或自动重放重启指令。恢复点及恢复耗时目标需后续确定。

内存快照冷启动后视为丢失：中控重新建立连接、重新采集并显示“启动中／重连中／等待采集／过期／真实失败”等区别，最新监控不承诺 10 秒内恢复；10 秒是常规采集目标而非恢复时限。跨重启任务按 §6.4 恢复和核实，不自动重复重启。


数据库版本尚未确定。建议使用共同支持的 SQL、短事务与索引，分别验证迁移、唯一约束、冲突及恢复；网络协议兼容不等于所有语义一致。

事务内不等待设备响应或重启。最后活跃时间可合并写入，不要求每次采样落完整快照；任务和审计仍可靠持久化。

审计关联操作者、目标、操作和结果，并同时记录中控原始墙钟、参考时间、来源、质量及时钟代际；不以板端墙钟作为审计顺序依据。使用中控进程代际与递增事件序号保留本进程内的因果顺序，跨进程排序同时保留数据库记录身份，不仅按可回跳的时间戳排序。NTP 回退、恢复、过期和跳钟作为独立事件记录，既有记录不回填改写。

审计不记录密码、私钥和凭据。初始密码只按第 3 节写启动日志例外输出，不进入普通审计载荷。任务和审计保留期仍需确定，持久化不代表无限保留。

## 9. Web 交付与安全

Vite 产物编译期嵌入二进制，发布运行不依赖 Node.js、静态目录或开发服务器。开发可使用 Vite HMR 和 API 代理。

建议缺前端产物时发布构建失败；哈希资源长期缓存，入口重新验证。SPA 页面可回退，API 和缺失静态资源不能错误返回入口 HTML。

中控只提供 HTTP，外部 HTTPS 反代可选而非必需。浏览器直连 HTTP 时，密码、会话和管理数据无传输加密，应限制在可信受控网络；板端加密不保护浏览器链路。

仍需安全密码哈希、会话过期、限速、CSRF 与 XSS 防护，但不能替代 TLS。纯 HTTP 不能依赖只在 HTTPS 发送的 Secure Cookie 完成直连登录，会话方案需按实际部署评审。

### 9.1 中英文与无障碍

管理 Web UI 继承 [PRODUCT.zh.md](../../../PRODUCT.zh.md) 的产品级约束，不设首版豁免：

- 简体中文与英文均为一等展示语言，支持切换与偏好保存；导航、表格、表单校验、权限说明、审批、风险确认、任务状态和时间质量提示均覆盖两种语言，不能中文硬编码。
- API、Protobuf、权限点、状态码、动作和审计事件类型保持稳定且语言中立；界面依据消息键和参数本地化，不让翻译文案成为鉴权或业务判断依据。
- 未知板端文案采用安全文本回退并标识来源，不作为 HTML 注入；缺翻译时显示稳定错误码或默认语言，不能导致操作状态丢失。

## 11. 容量边界

`/22` 有 1024 个 IPv4 地址，常规可用为 1022 个，其中还可能包括网关和中控。设计取约 1024 台在线设备，不把网段作为身份或授权边界，不强制同子网。

覆盖每设备一连接两条 gRPC 流、约千目标批量任务和集中重连。握手、待审批连接、队列、查询、执行及页面订阅均需资源上限。

具体并发、内存、速率和数据库配置在硬件、载荷与用户并发明确后压测；本文不宣称已验证容量。

## 12. 协议衔接与评审事项

### 遵守边界

- 业务动作、能力、去重和任务结果查询不视为传输规范已有实现。
- 小查询和 `tunnel.ping` 均按请求所在流回响应；`tunnel.ping` 是 `TYPE_REQUEST`/`TYPE_RESPONSE`，不是 `TYPE_SYSTEM` 或 `TYPE_EVENT`。
- 完成通知用 `TYPE_EVENT`，不用 `TYPE_SYSTEM`；事件禁止回包，补偿用独立查询。
- `tunnel.` 保留给协议动作：`tunnel.kick` / `tunnel.revoke` 使用 `TYPE_SYSTEM`，`tunnel.ping` 使用请求/响应；普通业务不得占用该前缀。
- 双流共享 TCP、连接流控和带宽，不能保证紧急控制永不阻塞；OpenData 首版即使无业务仍运行探测。
- HTTP/2 PING/ACK 连接健康、应用探测 dispatcher 健康、硬件采集/重启完成是三种不同证据，任务使用自己的 deadline。

### 待单独评审，不改变本次同步修订的其他密码议题

| 议题 | 原因 |
| --- | --- |
| 拒绝原因保护 | 服务端签名未覆盖 `reason_code`，它却影响是否停止重连 |
| 验签失败 | 立即断开与返回拒绝响应的描述需统一 |
| AEAD 失败 | 丢弃且不增序号之后是否终止连接需明确 |
| NTS 与更强时间源 | 未认证 NTP 只作参考，NTS 是否部署仍需确认 |
| 任务并发与超时 | 资源上限、硬件规模和业务 deadline 仍需压测与定稿 |

上述密码学议题仍未解决；本次不擅改密码签名布局或 AEAD 策略。

## 13. 后续验收目标

以下是设计目标，不表示已执行测试：

- 初始化只创建一次管理员，后端阻止未改密用户其他操作。
- 中控 NTP 启动预算最多 30s，失败 fallback 后继续 ready，后台有界指数退避重试；时间质量和板端时钟偏差语义可审计。
- 动态授权并集正确，撤权后能解释剩余来源；REVOKED 恢复必须管理员重新授权和板端人工重置。
- 批准不自动分组，批量审批明确选定公钥列表，不按 IP/SN 自动信任；健康 PENDING 不因审批久等被驱逐且资源有界。
- 目标去重固定、一目标一子任务、设备间并发与内部串行，后来者设备忙且不排队等待后续执行。
- 断线、超时、中控恢复和通知丢失不自动重复重启；冷启动不承诺 10 秒恢复，状态区分等待、过期与真实失败。
- 千台查询采用轮询错峰与过载跳过、限流和背压，不无限积压。
- `OpenControl`/`OpenData` 双向 `tunnel.ping` 使用请求/响应、nonce/trace_id/流代际匹配；HTTP/2 PING/ACK 与应用探测分别验收。
- 两种数据库分别验证迁移、关键事务和恢复；DB、私钥、配置分别安全备份并演练受控恢复。
- 英文和简体中文均为一等 i18n，Web 键盘焦点、对比度、减少动态效果和非颜色状态信号符合 PRODUCT.zh.md。
- 二进制脱离前端目录仍提供页面，API 错误不被 SPA 掩盖。
