## 1. 目标、信任角色与不可越界范围

- **外部操作者/可信授权来源**：独立于待执行程序和凭据提供者，签发或经受控渠道确认当次 `OperatorRecord`；其来源、信任锚、时间与撤销语义需要单独审定。记录逐引擎绑定批准目标、writer/O 内容 pin、O 精确 user 与 host、run id、窗口、操作 scope（只读预检与逐例 destructive reset/migration/case 分离）、传输策略及 TiDB 当前窗口拓扑核验；不能由工具生成 `operator_confirmed=true`、自身哈希、自签记录或 synthetic matched record 代替。未实现来源验证器时 **fail closed**，连受控根中秘密文件也不得打开。
- **无密构建器/启动器**：仅在单体载入任何秘密之前受信构建、独立验证 artifact 身份与依赖/加载链，然后 `exec` 唯一的 dev-only Rust 单体。它不读 secret、不传 URL/password/授权自证、不作为运行时父监护者。受版本控制的源码及独立不可改写的部署 artifact 是交付前提；自身计算 SHA-256、仅 pin inode 或工作树中同 UID 可原位改写的二进制不是独立构建证明。是否满足同 UID 修改、动态库、环境、`/proc`/ptrace 信任边界由外部确认；否则拒绝 live。
- **Rust 单体 OS 进程**：授权验证、受控文件打开与 pin、writer/O 门禁、双目标 alias、锁/备份回执、每例 O preflight、reset、原库迁移 API、严格 v3 fixture、A/B/O 会话、四个实际函数及结果/journal 全部在此进程。可用 Rust 线程/async task，包括同进程 watchdog；不允许第二个载密 OS 进程或以线程冒充独立进程监督。**载密后从可达调用图禁止** `Command`/shell、Cargo、probe、migration binary、libtest executable、其他 test child、构建脚本；关闭 O fd 后启动 child 也不例外。无密构建器不能在单体载密后再接管流程。
- **业务参与者**：每例 A/B 是原 writer 同一身份、两条独立且固定的物理连接；O 是独立最小只读身份的第三条物理连接，诊断不经 A/B 发起。fixture/迁移及 preflight 使用的连接是额外短期连接，不能声称整个进程严格只有三连接。不得改变原 writer grants grammar、旧 callers 或新增 MySQL `performance_schema`（P_S）授权；现有 writer 读 P_S 返回 1142 是拒绝理由，不是扩权理由。O 不能传给 `AdmissionStore` 或替代原 CAS。原账号权限不由工具创建、GRANT 或 REVOKE。
- **执行范围**：仅明确获准的隔离可丢弃开发目标，保留双目标实际隔离/外部停写、多确认、真实备份、精确目标、仅表级 reset；绝不 `DROP DATABASE`、自动补建数据库、改生产连接或隐式更换引擎。选择单引擎时如另一配置存在也要做跨目标 alias 检查；单引擎结果不得冒称四例两库通过。MySQL 8.0.46 的验收不替代 8.4 LTS，TiDB 版本和拓扑亦不得推断。

## 2. 模块边界及最小接口契约（非实现清单）

新入口应为**受版本控制的 dev-only Rust 可执行源码**，静态注册四个可调用函数；不能以 `.superpowers/dev-db-probe` 下被忽略的现有入口作为唯一可复现交付。概念接口分成：`TrustedRecordSource → VerifiedRun`（当前来源验证器不存在，live 构造与执行分支硬编码拒绝，不允许运行时开关、caller 可构造的公有 `VerifiedRun` 或把 fake 注入 live）；`ControlledOpener → PinnedWriter/PinnedObserver`（私有同一 bytes）；`TargetGate`（原 writer 权限、alias、锁、当前状态真实备份回执/ACK）；`ObserverPreflight`（只读身份/grants/roles/scans）；`TableReset`（唯一 tracked 核心的白名单/元数据核验）；`run_identity_test_migration(&TestMigrationConfig, TestMigrationMode::Upgrade)`（现有公开库 API）；`FreshV3Gate`；`CaseRegistry → CaseA/CaseB`；`RunJournal/Watchdog`（持久化状态/硬超时）。每个输入只接受前一层不可由调用方构造的已核验绑定；不给通用 SQL、路径或任意 case name 解释器。将来独立设计并批准 record 来源、验证密钥/信任锚、时钟与撤销、跨 `exec` 受信传递及单体在同一授权窗口内重复验证后，才可另审解除固定拒绝；同一程序签发、自签 hash、stdin envelope、布尔字段或纯 fake 均不能通向 live。

[原 probe](<../../../.superpowers/dev-db-probe/src/main.rs>) 已审 parser、writer 预检及 `main.rs:910–986` 表/FK 白名单/reset 必须搬至**一个 tracked dev-only Rust 核心模块**，由 tracked 单体入口调用；旧 ignored probe 要么改为调用同一核心且不可让单体依赖 ignored 文件，要么明确退休旧历史执行模式，绝不能保留独立可运行的第二套 parser/reset。clean checkout 不用 `#[path]` 等形式引用 `.superpowers/*` ignored 源，不能复制一套后仅交付新 main；实施前另审 manifest/lockfile、依赖许可/MSRV、加载链和不可原位改写的构建/部署身份，不原位重写外部 artifact/依赖。旧 Python runner、ignored probe 和 O-only 子进程不是新 live 入口。对 [测试 common](<../../../crates/rsetup-controller/tests/common/mod.rs>) 仅抽出 Task4 必要 fixture、业务断言与两个并发 helper 至 tracked test-only 可调用模块，暴露四个静态注册函数；`fixture_ok` panic、assert、timeout/drop 控制流须改为可判定结果/unknown，不能直接搬作安全 live。全载密可达调用图涵盖单体、生产库、test-only helper 和构建/加载链，排除 `run_explicit_identity_test_command` 的 `Command::new` 等 spawn。原 `run_identity_test_migration` 已是同进程公开库 API，其 `TestMigrationConfig` 可在私有内存构造并保留前后 `authorize`、真实 `DATABASE()` 与 writer 权限检查；不重写迁移 DDL、改为通用 SQLx Migrator 或仅填非空 `backup_ref` 冒充备份。库函数自身另开连接并执行可能非事务的多条 DDL：按用户裁决**不改为逐 SQL journal hook**、不修改生产代码；在调用整个迁移/CAS 之前先独立 fsync 一次固定去敏操作 intent，覆盖其所有内部 DDL/DML/commit，任意部分、超时、未知发送或 commit 结果一律 `unknown`、停两库人工核验，明确成功仍需实际持久状态断言与完整 journal；逐条 fsync intent 仅适用于单体自己直接执行的 SQL（受控 reset 每次 DROP、fixture 各 INSERT、受控 A 停用 UPDATE/commit），不能暗示已知道生产内部哪一步已运行，也不能凭函数 `Err` 自认为回滚。库函数对服务 URL 的字面等值检查不证明物理隔离，外部隔离另核。连接 URL 不进 argv/env/普通日志；不在多线程 Tokio 运行时修改进程环境变量。若现有 API 无法在保持门禁的前提下安全复用，本次单体方案即固定拒绝该动作；任何极窄内部参数接口调整都必须作为**另一份方案**先经独立审查和用户单独书面批准，当前规格不授权修改生产代码、移除原校验或添加逐 SQL hook。

[observer 支持](<../../../crates/rsetup-controller/tests/support/observer/config.rs>) 中纯 bytes `prepare`、O grants/查询 catalog 和真实 transport 可有限复用；旧 `handoff.rs` 的跨进程 `unsafe FromRawFd`、`pass_fds`、artifact fd/stdin envelope 不迁入新单体。Rust 自受控根安全直接打开并持有 `File`/`OwnedFd` 的独占所有权（需要 bytes 时读取同一 owned 文件），不是接收裸 fd/猜测编号。旧 `observer.rs` 真实入口当前固定 `prerequisite_missing`，其 fake serializer 的 passed 并非真实 preflight。共享接口要求真 adapter 与 fake 走相同业务顺序；只检查文本/调用图不能证明 SQLx 在真实 MySQL/TiDB 解码成功。

## 3. 从无密到单体会话的严格时序

1. **无密阶段**：检查封闭 CLI（只接受预定义 batch 或经另批的明确子集）、受信构建证据、危险继承环境和受控根、可信时间、目标/窗口/scope，以及 `OperatorRecord` **独立来源和完整性**。无该来源固定拒绝，0 secret opens/0 connections/0 reset。无密 builder 仅在此边界完成构建验证与 `exec`；单体随后亲自重复独立授权核验。来源/外部记录不能来自同一秘密文件、命令行布尔或旧 Python envelope。构建仅在载密前另获批准并有独立上限；单体内从首次授权/受控打开/全局备份与 writer gate 开始即启动首例 pre-t0 保守硬300秒预算，不得先无界执行全局阶段再为首例另起预预算。
2. **取得本次已核验授权后才按 scope 打开文件**：从固定受控根的目录 fd 逐组件 nofollow 打开 writer 与 O 文件，拒路径替换、软链接、不可信可写祖先/目录、非本地可信 owner、非私有 mode（目录 0700 或更严、regular file 0600 或更严）、空文件或超过 64 KiB。读前后 `fstat` 和身份/大小/修改状态漂移必须拒绝；在每份单次读入的**同一 bytes**上先核本次授权的全长小写 SHA-256 pin 后严格解析，绝不按路径二次读取另一版本作迁移配置。再次需要配置时，重新受控打开并比对本次授权 pin、目标和当前窗口；不把旧成功缓存成新授权。旧 writer schema/字段不宽松化；O JSON 仅 `username`/`password` 两个非空字段，拒重复、未知、host/port/database/URL/TLS 覆写。内部保存资源 RAII，不把 bytes/password/URL 写到结果。
3. **破坏动作前的全局及逐例门禁**：即使选一个引擎也比对存在的两个目标配置的规范 host/port/database，拒别名（仍需外部证明物理隔离）；持有受控私有结果目录及 nofollow、0600 `.runner.lock` 的独占锁直到整轮结束。锁只排斥本工具实例，其他操作者停写另证。每个 case 的每次 reset（包括第一次空库）都必须由当次获准的**真实、可恢复、覆盖将被 reset 的整个当前对象及数据状态**的备份文件、receipt 和独立的外部当前状态一致性/独占证明先行授权；对 engine、精确实际目标、备份范围/时点、内容 digest、恢复可行性和 live 当前状态做可判定一致性检查，并在 reset 前重核状态未漂移。意外数据、状态变更、无外部可信证明或来源不可确认直接拒绝/人工核验，绝不自行生成、自动补写备份/receipt、复用过期 SHA 或只凭 receipt 布尔值作 ACK。首例空库不是例外：不接受原 no-op 注释-only `backup-empty` 逻辑导出工件（原 probe `main.rs:143–157` 零对象注释文件、无 DDL/DML）及其 receipt，不得凭旧 v1 receipt 的 `backup_verified:true`/文件 SHA-256 通过而放行；必须由独立可信来源出具、可独立验证的实际可恢复工件（覆盖 reset 前目标库全部当前对象/数据/相关元数据；空库即“同一无对象库”的可验证证明），连同该 receipt 与目标当前状态一致性证明，恢复语义不得要求 `DROP DATABASE`，恢复可行性由独立可信来源的可独立验证工件/receipt 证明，本工具不自测自评；无该工件/receipt 时，若 `OperatorRecord` 来源已获验证，由备份门禁在**任何 reset 与 O preflight 之前**（即 pre-t0 门禁内）拒绝，若来源仍不存在则更早的零凭据拒绝先行。首次 empty-schema receipt 的 `empty_objects_confirmed` **只能**对应当时确证的空状态，不能覆盖下一例已建 v3/actor/device；当前 v1 receipt 格式不能表达非空状态，必须先另行批准和定义由独立可信来源出具的**当前状态** receipt、一致性证明及验证规则；在此之前任何后续非空 case 固定拒绝，即使前例 passed 也不能以可丢弃为由放宽；后续非空例的 receipt 来源格式与可恢复验证需另行批准，未定前固定拒绝，且不得程序生成或自动补写。原 runner 仅在每目标开始调用一次 `verified_backup()`、后续复用初始 receipt 逐例 reset 的历史行为，与**用户批准的新收紧门禁**冲突；新入口不得沿用。receipt 本身及备份文件须从私有受控目录 fd 逐组件 nofollow 打开，要求 regular、可信 owner、0600 或更严、大小有界（receipt ≤64 KiB，备份上限须由外部为获准目标明确设定，未定则拒绝），核其读取前后 `fstat` 的 inode/大小/修改等 drift、同份 bytes 全长 SHA-256 与 receipt 绑定，不走 symlink check 后路径再开的竞态。不可把 hash 匹配、私有文件、锁或 receipt 自述当外部的备份可恢复/当前一致性证明。固定 migration ACK `isolated-exclusive-backed-up-disposable` 仅在本次 reset 与随后 migration 所需**当前**门禁同时成立后供原 API；保留 writer 原有 `direct_database_all`/实际目标/metadata preflight 与原权限，不能让 O passed 代替它。
4. **每个 case 的 O preflight 真正起点 t0 前与 t0 后**：先在独立 pre-t0 有限预算内重新检查 record 来源/窗口/逐例 scope、双 pin、传输/拓扑、当前状态备份/receipt/外部一致性与原 writer 预检；`actual_writer` 必须来自**该次真实 writer 物理连接的非 NULL `CURRENT_USER()`**，绝非 caller 字符串、config 或 grants 文本。pre-t0 从进入该例首个门禁起设**硬 300 秒**保守独立上限，所有等待受最早剩余预算/单连接 10 秒/单查询 3 秒约束；这是待整篇批准的**新增设计选择**，不是已批准 case300 的一部分，也不是延长/重置 case300。任何预门禁失败/超时在确认未发 reset 请求时 `reset_attempted=false`、全批停；不能无期限停在密阶段。上述门禁成功后，立即在尝试建立/复用本例 O 无默认库独立物理连接**之前固定 t0**并同时启动 case300 绝对钟；连接建立和 O 的 `CURRENT_USER()`、`CURRENT_ROLE()`、MySQL `mandatory_roles`、`SHOW GRANTS` 封闭语法及指定每张诊断表/视图非恒假 `LIMIT 1` 真正只读扫描均属于 t0 后 O preflight。空结果只证明请求成功，不证明 edge 或行解码；任何 preflight 失败/超时且未开始 reset 时标 `reset_attempted=false` 并全批停。只读预检不得发 `SET/USE/BEGIN/FOR UPDATE/DDL/DML` 或任意输入 SQL；适配连接须关闭 SQLx 默认初始化 SET/statement logging。所有实际身份不能为空、不能靠 config/grant 字符串代填。每例都重新做，不能复用上例 success JSON。
5. **经 journal 先行后破坏动作**：在 case300 内持久化固定去敏 `reset_intent` 并确认 fsync，随后由唯一 tracked reset 核心先核验精确目标、对象白名单、FK 拓扑及对象数，返回已核验的固定表顺序；**核心不得在不可见的内部循环发出 DROP**，由单体在每张表的请求可能发出前各自 fsync 去敏 intent，再逐条构造并执行仅限获准目标的 `DROP TABLE`，最终复核零对象；不 `DROP DATABASE`。reset 每次 DROP 均为单体直接执行、各自预先持久独立 intent；只要 `reset_intent` 已 fsync 而无法证明绝未发出请求，就以 reset 可能发出判 unknown，绝不伪报 `reset_attempted=false`。随后同进程调用原公开库 `Upgrade`（不改为逐 SQL hook）：调用前先独立 fsync 一次固定去敏操作 intent，覆盖其所有内部 DDL/DML/commit；调用后仅验证 fresh v3 十一表、schema_meta 单例及无 CHECK/FK 等严格**未插 actor/device 的 v3 基线**，实际持久状态断言通过且 journal 完整才可判成功；任意部分、超时、未知发送或 commit 结果一律 `unknown`、停两库人工核验，不能暗示已知道生产内部哪一步已运行，也不能凭函数 `Err` 自认为回滚。任何迁移 DDL 错误保留实际状态而不自动 reset 清理；总 case300 从 O t0 不重置。
6. **先核会话再插业务 fixture，插后再核**：严格 v3 基线完成后建立 A/B 固定的原 writer 同身份连接与 O dedicated 无默认库连接，验证各自实际 `CURRENT_USER()` 非 NULL、O 与 record 精确 user/host 相等且与 writer 不同，A/B 与 preflight 同次 writer 实际身份相等，三物理 ID 两两不同、无静默重连，A/B `DATABASE()` 是精确目标而 O NULL。会话身份、连接和拓扑先验通过后，**才**用原 `task4_concurrency_fixture` 的 actor/device 插入语义和原完整 snapshot/events/meta 比较建立业务夹具（必须抽为受控可返回结果接口而不改变业务效果；每次 INSERT 前独立 intent）；然后在业务开始前重核 A/B/O 身份、连接 ID、当前窗口拓扑及 fixture 完整性，任一失败停。原 helper 实际为先建 A/B、检查 ID，后插 actor/device；新抽取禁止提前插入或误称 v3 schema 已等于业务 fixture。MySQL 精确版本、同次获准实例绑定的 UUID、A/B 实际 `DATABASE()`、P_S 唯一 thread 映射只由 O 诊断查询；TiDB 精确版本、当次可信控制面同集群/无跨路由核验、三会话真实 global-kill、A/B pessimistic 与真实 session ID/start_ts 绑定。O preflight 连接仅在保持同一物理连接且重核身份后可作为 O；不得以前置旧证据替代插后重核。A/B 不读 P_S/TiDB 跨会话诊断视图，正向 edge 仅由 O 固定 catalog 读取；O 不传 `AdmissionStore`。保持可证明的 TLS policy/host/cert 与旧 writer 连接语义；SQLx `Preferred` 可能降级，options 相同不证明实际 TLS，不满足获准策略时停下另审，不悄悄改字段或新增 endpoint。
7. **运行静态四例并持久判定**：顺序和映射固定，首失败/未知立即停止此后所有 case 与另一引擎，未运行独立记 `not_run`。无自动重试、自动恢复状态、失败后新 DROP 或挪用另一个授权窗口。成功应是实际函数返回且全部持久断言通过，不把仅建表或 fake preflight 标 passed。

## 4. 权限闭集、等待证据与四个函数

MySQL O 只接受各一次 exact `SELECT` on `performance_schema.data_lock_waits`、`performance_schema.data_locks`、`performance_schema.threads`，可选一次 `USAGE ON *.*`；TiDB O 只接受 exact `PROCESS ON *.*` 一次，可选 USAGE。两者拒 wildcard/mixed/duplicate/dynamic grants、角色/proxy/GRANT OPTION，拒未知/NULL/重复的 grants 形态；`CURRENT_ROLE()` 只接受已审版本对应 `NONE`，MySQL 全局 `mandatory_roles` 必须空；TiDB 不发明同名 sysvar，由操作者核验外部强制权限注入。严格完整 account 解析保持 user/host 分字段，shape 变更须另审，不在 live 宽松回退。SHOW GRANTS、身份、roles、实际扫描各自独立成立。TiDB `PROCESS` 和 MySQL P_S SELECT 可看到其他用户/库的诊断元数据，固定最少列与 no raw output 并不等于 DB 层行列隔离。

MySQL O 以当次 A/B connection/thread 和 schema_meta 精确二进制 schema/table 关联 `data_lock_waits → threads → requesting data_locks`，正向 B waiter→A holder，拒重复/歧义；不使用 O 的 `DATABASE()`。TiDB O 以真实 A/B `SESSION_ID` 唯一映射当次 `start_ts`，`DATA_LOCK_WAITS.TRX_ID → CLUSTER_TIDB_TRX.ID` 和 `CURRENT_HOLDING_TRX_ID → holder.ID`，只在服务端校验 JSON 有效并提取精确 schema_meta，原始 KEY_INFO/SQL/行数据不出进程；holder 映射缺失/重复拒绝、waiter 尚未进入可在预算内继续，最终必须有唯一正向边。相同 host/port、UUID 或备份不能自行证明 TiDB 同集群；真实 SQLx `CAST` 返回类型/角色格式、版本/权限/边需后续各自单独实测。

静态注册表依次且仅有以下四个精确标识，拒近似名、重复、0 个和跨引擎错配；它们映射到真实 Rust 函数，**不调用 libtest，不保留原 wrapper 作为新 live 入口**。旧四个 ignored wrapper 仅可保留为历史测试，不是新单体批次的许可入口，不会由新单体调用；它们仍执行 spawn 外部迁移 child 的旧手动路径，其结果不得标为新四例通过；单一 tracked 安全核心不可保留第二套 live parser/reset：

| 顺序 | 注册标识 | 函数效果 |
| --- | --- | --- |
| 1 | `admission_deactivation_holds_guard_cas_waits_then_denied_on_fresh_v3_mysql_observer` | MySQL Case A |
| 2 | `admission_cas_commits_before_deactivation_then_new_cas_denied_on_fresh_v3_mysql_observer` | MySQL Case B |
| 3 | `admission_deactivation_holds_guard_cas_waits_then_denied_on_fresh_v3_tidb_observer` | TiDB Case A |
| 4 | `admission_cas_commits_before_deactivation_then_new_cas_denied_on_fresh_v3_tidb_observer` | TiDB Case B |

Case A：A 原 writer 事务按 `schema_meta` guard→users 行顺序停用 actor（未提交）→ barrier 放 B 调**原生产** `AdmissionStore::compare_and_set`；**O 而非 A** 在 A commit 前看到 B→A schema_meta 唯一正向等待边并确认 B 未提前结束，才允许 A commit。B 必须精确 `PermissionDenied`，设备原 snapshot 与完整 history/audit/meta business values 不变，actor inactive/revision 8 持久。正向等待边不是 sleep、等待态或 fake boolean；schema_meta 单例归属依严格 fixture 与固定 SQL，不虚称逐行 lock key 独立验证。A 的 guard 与 users `SELECT … FOR UPDATE` 加锁读若在中断后无法确认连接/事务已释放，也归入 `unknown` 兜底，不凭尚未写 UPDATE intent 就推断 A 事务从未开始；A 的 UPDATE/commit 仍为单体直接执行，各在请求可能发出前分别 fsync 独立 intent。生产 CAS 为调用前一次粗粒度调用级 intent，覆盖其内部全部写入与 commit；边缺失、B 提前返回或 commit 结果不明均不能 passed。

Case B：B 原 CAS 先 commit，立即持久验证 approved/revision 2、恰一条 history/audit 及完整业务值，**首次持久断言全部完成才**放 A 停用并 commit；此后 B 新 CAS 必须精确拒绝且设备/完整 events/meta 不变、actor inactive/revision 8。首次与第二次 CAS 各在调用前先持久一次粗粒度调用级 intent（覆盖内部全部写入与 commit）；A 的 UPDATE/commit 为单体直接执行、各在可能发出请求前先持久独立逐条 intent。Case B 要 O 的前置身份/能力和实际三会话验证，但**不**增设反向等待边。两例旧 helper 的 `fixture_ok` panic、`assert!`、`tokio::time::timeout`/`try_join!`、drop 均不得直接当安全 live 控制流；结构化取消并有界尝试 rollback/关闭，依服务器可核验结果分类。只有确认未发请求或明确回滚且验证无持久副作用的失败才可记 `failed`；已发 CAS/commit、rollback 或关闭未确认、取消/超时无法证明结果者一律 `unknown`，不能凭 drop 或 hook 推定回滚。产出绝不包含 fixture 行数据。

## 5. 同进程 watchdog、预算与不可伪造的状态

连接最多 10 秒、单 query 最多 3 秒；每例的**真正 t0 是 O preflight 开始**，从 t0 到最终持久终态为**总 300 秒**，O 30 秒协作绝对截止、同进程 O 45 秒硬截止、reset 自开始 90 秒硬截止、业务 barrier/channel/O 采样 20 秒均计在该总时钟内；每一步取单步上限、阶段截止和 t0+300 秒三者**最早**剩余量，不能因 reset/migration/fixture/业务阶段切换重置总钟。采样 100ms 仅限流，绝非边证据。t0 前每例 record/备份/writer/拓扑等门禁有独立的保守硬 300 秒上限（待整篇书面批准的新增设计选择，并不算入已批准的 case300），包括密阶段等待，超时不得继续；即使全部 pre-t0 门禁临界完成也必须从实际 O preflight t0 才启动总钟。watchdog 为同进程独立 Rust 线程检查单调绝对钟；**Linux 硬出口使用全线程立即退出且不等待 `atexit`/析构/线程 panic 的 `exit_group` 等价 `_exit`，不是 `std::process::exit`、panic 或等待 async cancel**。任何秘密载入前禁用 dumpable 且设置 `RLIMIT_CORE=0`，实施前须另审原语、权限/失败判据、core 及加载链风险；禁用失败或非 Linux 环境无法保证相同语义时拒绝 live。到最早硬截止即 fail-stop，不得为 journal/rollback/close/JSON 等待；硬截止前若能有界取消、证实 rollback/关闭并 fsync 去敏 `stop_unknown` 可正常结束，否则硬退出允许缺终态记录。已发数据库请求、commit/rollback 或关闭未确认均按 unknown，不把硬退出当回滚。watchdog 并非外部监护：SIGKILL、SIGSTOP、宿主停顿或线程不可调度不保证墙钟准时退出/补写日志，外部按 unknown；无 cgroup 备用方案。

受控私有目录内去敏 journal 采用独占创建、受限权限、无跟随、序号/前序 digest 连续绑定的追加记录，逐条 fsync 及必要的目录 fsync；锁定当前授权的唯一 run id、固定 engine/case/stage 顺序及版本。首次只有已验证私有目录内**不存在任何历史 journal/未判明 intent**且锁已取得时，才可独占创建本轮新 journal 并先 fsync `authorized`；既有或本轮 journal 的预期记录缺失不得当作新运行。创建后及进入下一例前必须完整 replay：缺记录、截断/损坏、**撕裂（half-written）末条记录**、序号或 digest 断裂、重复/旧 run id、receipt/授权/目标绑定不一致、已存在未判明的旧 intent，**一律拒绝新的破坏动作并按 unknown 人工核验**；不得覆写、补造或靠重试“修复”日志，也不能把 journal 视为外部停写或 DB 成功证明。最小事件包括 `authorized`、`case_preflight`、`reset_intent`（每条）、`reset_may_have_started`、`migration_call_intent`（一次，整个 `run_identity_test_migration` 调用前，覆盖其所有内部 DDL/DML/commit）、`fixture_insert_intent`（每条）、`business_write_intent`（单体直接执行的写 SQL 每条，含受控 A 停用 UPDATE）、`cas_call_intent`（每次生产 `AdmissionStore::compare_and_set` 调用前各一次，覆盖其事务内全部写入与 commit）、`commit_intent`（单体直接 commit 每次）、`fixture_may_exist`、`case_running`、`case_passed`、`stop_unknown`；逐条 intent 仅适用于单体自己直接执行的 SQL（reset 每次 DROP、fixture 各 INSERT、受控 A UPDATE/commit），在**请求可能发出之前**独立 fsync intent，失败不发 SQL；生产 `run_identity_test_migration` 与 `AdmissionStore::compare_and_set` 不插入逐 SQL hook，只做整调用前粗粒度 intent（粗 intent fsync 失败同样不得调用生产调用），明确成功以调用后实际持久状态断言通过＋完整 journal 为准，任意部分、超时、未知发送或 commit 结果一律 `unknown`、停两库人工核验，不能暗示已知道生产内部哪一步已运行，也不能凭函数 `Err` 自认为回滚。可选固定回执事件仅记录本进程已观测确认，**不证明 DB 实际提交或撤销**。输出仅固定 engine/case/stage/class、枚举状态、去敏布尔/计数和非敏 run 引用；不收 raw SQLx/OS error、schema/host/account/URL/grants、session ID、拓扑明文、备份字节或 fixture 数据。stdout/stderr/崩溃钩子同样只能输出闭集标签，不允许 SQLx statement logging、panic payload、`Debug`、异常链或环境变量绕过；禁 core。批次结果每 case `selected/executed/passed/failed/not_run` 实际计数、`reset_attempted`、`fixture_status:{not_started,known_preserved,unknown}`、`result:{passed,failed,unknown,not_run}` 及固定 `stage/error_class`；缺失终态只能推 unknown，绝不从缺 JSON 推断 `reset_attempted=false`。

状态分类以**已持久的最保守先行事件和可核验的外部事实**为准：pre-t0 或 O 前置失败且从未持久破坏 intent、可证明未发出写请求时 `failed`、`reset_attempted=false`、`fixture_status=not_started`；`reset_intent` fsync 后即对外 `reset_attempted=true`（含 SQL 可能尚未发出的情形），直至 reset 是否真正执行、是否完整持久、后续写/commit/rollback 是否生效有充分 DB 证据前都按 `unknown`，不可由 intent 单独推定 DB 已提交；明确确认失败且核验没有悬置写请求/未确认事务、并持久固定失败结果时才可 `failed`。确认业务 passed 必须真实函数全部断言成功、相应数据库状态可复核、journal 完整 fsync；成功后 fixture **留在原位**标 `known_preserved`，不是“已清理”。若失败时可靠已知 fixture 留在原位亦标 `known_preserved`，不确定则 `unknown`；此字段不覆盖 `result=unknown`。已经发出 SQL、非事务 DDL、未知 commit、rollback/关闭未确认、日志缺口、watchdog 硬退出、外部 SIGKILL/崩溃都可能留下未知数据库状态，fd 被内核关闭不是回滚或外部停写证据。unknown 是吸收态：停两库、不得自动 reset/清理/重启续跑；人工核验实际状态及**新当前状态真实备份/receipt**、新窗口重新授权后才可进入另一轮；粗粒度调用级 intent 已 fsync 而生产迁移/CAS 结果部分、超时或不明时，即使函数返回 `Err` 也一律 `unknown`；进程死亡（含 SIGKILL）不构成授权，锁可被内核释放而旧 journal 仍在目录，不得推定安全或重新执行，必须经本吸收态人工核验与新一轮授权。

四例计数仅来自静态注册函数调用进入/返回及其持久结果：完整成功为 selected=4/executed=4/passed=4/failed=0/not_run=0（每库 2）；首失败仅实际进入的函数算 executed，未运行余项只计 not_run；入口被拒时 executed=0。不能打印 `1 passed/0 failed/... filtered=total-1` 等伪造 libtest summary，不能把 fake 通过、未选择或预检成功记为业务通过；异常而执行结果未知不得冒充 failed 已证实持久状态。选子集（若后续明确批准）只声明该子集，不能宣布双库四例验收。
