## 1. 页面范围

| 页面 | 内容与限制 |
| --- | --- |
| 登录 | 本地账号、统一失败文案、限速反馈，不开放注册 |
| 强制改密 | 只改自身密码/退出，不加载其他业务数据 |
| 设备列表 | 分页、可见设备、授权投影；最小身份与详细状态分开 |
| 设备详情 | 档案、能力、准入、连接、流健康、最新状态、时间质量按权限显示 |
| 批量重启确认 | 固定清单、检查结果、风险与总目标；不因实时组变化加入新目标 |
| 主任务/子任务 | 逐状态进度、结果证据、unknown、取消边界与授权子集标识 |
| 准入审批 | 公钥/指纹/描述/连接、分页和显式批量清单，管理员专用 |
| 设备组 | 成员变更提醒会动态改变权限，管理员专用 |
| 用户/角色/授权 | 最后管理员保护、权限来源、有效权限预览，管理员专用 |
| 审计 | 操作者、目标、结果、时间来源/质量，管理员专用 |
| 系统状态 | NTP退避/质量、资源与恢复模式，管理员专用 |

UI隐藏不能替代后端鉴权。用户有reboot无read时，只展示其最小设备识别和允许的操作，不请求无权详情。任务授权子集不显示隐藏数量；创建成功不保证能读取详细任务。

## 2. 状态与风险呈现

U-01：准入、连接、业务流健康、监控新鲜度和时钟质量分别呈现。不得以一个绿色“在线”表示所有业务正常；保活成功不代表任务成功。

无采样为等待采集/unknown，超过阈值为stale，有采集失败为error，不能用0填未知。默认“最近收到”按中控接收证据，板端时间保留来源/偏差/质量；未校准、回跳和NTP回退显式提示。

重启流程：选择→预览固定清单→风险确认→创建主任务。客户端重试保留Idempotency-Key；不能因202或掉线就显示成功。unknown显示“结果未确认”，不以失败文案诱导自动重试。

取消只影响queued/held；dispatching后明确不可保证撤回。管理员释放unknown占用须再次确认可能已经重启，保留原结果，不自动提交新操作。

吊销/重新授权页面提示板端人工重置要求，不宣称中控点击即可恢复在线。中控启动NTP关卡期间只有启动日志；ready后快照冷启动不承诺10s全部恢复。

## 3. 双语与无障碍

U-02：简体中文与英文均为一等语言，覆盖导航、表格、表单校验、权限、审批、危险确认、错误、任务及时间质量。支持语言切换与偏好保存；语言切换不改变设备选择、幂等键、权限判断或任务语义。

API、权限点、状态码、动作和审计事件类型语言中立；UI用message_key/params翻译。未知板端文案按纯文本安全回退，缺翻译显示稳定错误码/默认语言，不丢失状态，不把文本注入HTML。

所有主要流程可键盘完成；焦点清楚，弹窗打开/关闭正确转移和恢复焦点；状态不能只靠颜色。尊重对比度与减少动态效果偏好，桌面/窄屏均容忍中英文本扩展；文档语言和无障碍标签随语言更新。继承PRODUCT，无首版豁免。

## 4. SSE与缓存

U-03：本稿拟议SSE，只作变化提示/授权投影，不是持久消息总线，也不是板端双向Ping/Pong。

事件类型：`device.updated,task.updated,permissions.changed,system.time.changed,reset`。数据携带对象ID/revision及可见字段；时间事件仅管理员。发送前验证session与authz_epoch，撤权关闭旧订阅，排队旧权限数据不得发送。

每连接建议最多128条待发事件；满时发送reset或关闭，客户端GET重取当前状态，不能阻塞板端采集。Last-Event-ID仅用于断档识别，不保证历史重放；初次打开/重连时先建立订阅并缓冲事件，再GET快照，丢弃不高于快照revision的缓冲事件后应用较新事件，避免“先GET再订阅”之间漏掉唯一终态通知。订阅建立失败或收到reset则重新同步，不把本地结果宣称为实时。token不放URL，使用cookie。

页面网络断开显示连接状态，不能把旧快照当实时；组件卸载取消订阅，不为每个页面启动独立板端轮询。前端刷新/语言切换不创建任务。

## 5. 内嵌交付

U-04：Vite生产构建先完成，Rust编译时嵌入全部静态资源。缺产物发布构建失败，不生成“能启动但无管理页面”的发布包。运行无Node.js、静态目录或开发服务器。

管理页面/API同源，只提供HTTP；外部HTTPS代理可选，不是必需依赖。开发可Vite HMR/API代理，不影响发布二进制约束。

内容哈希资源长期缓存，入口重新验证；页面路由可回退index.html，缺失静态资源及/api错误不得回退HTML。响应正确Content-Type，未知页面与权限错误明确处理。前端依赖候选不意味着已完成选择与安全审计。

## 7. 容量与故障报告

拟议基准：1024已批准设备、20管理会话、RTT≤100ms、稳定1h，99%的状态采集间隔≤15s，所有队列/连接/未决项不超配置；另测1024首次PENDING部署。目标是审阅值，不是现有性能承诺。慢设备场景单独验证重启吞吐下限：核实阶段占用并发槽，16槽×5min观察窗口的理论上限约16台/5min，需压测确认可接受。

报告必须记录中控CPU/RAM/OS、数据库产品/版本/资源、板端模拟规模、状态报文大小、RTT/丢包、浏览器数、参数配置、吞吐/延迟分位、最大内存与拒绝计数。不固定硬件却宣称“支持1024”不算验收。

故障注入包括NTP和DB离线、网络丢包/延迟/重连风暴、握手洪峰（未认证上限与全局握手限速的叠加行为）、慢消费者、半开流、OS回跳、各发送/落盘崩溃窗口和旧备份恢复。故障时不强求正常采集间隔，但必须资源有界、状态诚实、不越权、不自动重复变更。

## 8. 审阅与发布

完成上述功能验证仍不自动消除00列出的传输安全阻断。上线前分别审阅协议安全、HTTP部署风险、数据库兼容矩阵、备份恢复记录和板端持久日志语义。未验证硬件能力、合成数据和结果未知必须始终明确标注。
