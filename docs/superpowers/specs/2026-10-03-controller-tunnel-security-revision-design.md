# Controller 隧道安全修订设计（待审，2026-10-03）

> **状态与效力**：本文只记录人类已确认的**待审设计方向**，不是现行协议、实现许可、独立安全审查结论或测试通过证明。当前 `docs/protocol_spec.md` §4.1 的握手版本仍为 `0x02`；在用户复审、独立安全专家审查、协议原文及计划同步修订、双端实现审查和测试完成前，认证隧道、传输实现与生产发布均保持阻断。本文不修改既有规范、计划、CI 或源码。

## 1. 背景、边界与选择

现行 `docs/protocol_spec.md` §4.3 的服务端签名含 `status`，却未覆盖决定板端是否自动重连的 `reason_code`；§4.1/§4.5 既要求验签失败立即断开，又在时序图中返回 `REJECTED(SIGNATURE_INVALID)`；§5.2 规定坏 tag 丢弃、不增加 `RcvSeq`，但未决定是否继续同一连接。`docs/superpowers/specs/2026-09-23-controller-v1-00-index.md` §6 与 `docs/superpowers/specs/2026-09-22-controller-design.md` §12 将三者列为发布阻断。`docs/superpowers/plans/2026-10-02-controller-02-transport-board-tdd.md` 的 Global Constraints、Task 3/4、Task 9/10 和最终联合门同样禁止以局部进度替代协议修订及双端证据。

此处采用**新显式版本 `Ver=0x03`**：不是给现有 `0x02` 消息暗加字段或静默修补，也不自动回退。选择域分离、签入拒绝原因及失败即终止整条 TCP，而不是在已污染连接上重同步；这样可分别验证旧版拒绝、签名语义与失败状态。`Magic=0x53,0x45`、8B 帧头、`FrameType=0x01` 至 `0x06`、握手 Payload ≤16KiB、§4.1 的严格时序与 PENDING 的 5s/10s/15s 单调计时、§4.4 的 X25519 检查仍按既有规定拟沿用；不是在此批准这些现有设计的安全性。§5.1 的 HKDF 参数和 §5.2 的 Nonce/AAD 布局拟保持原样，仅补充失败终止规则；业务 h2c 仍只能在最终 `APPROVED` 且**双端认证及密钥协商成功后**于同一 TCP 上启动（§4.5、§6.1）。

## 2. v3 握手的字节与语义契约

### 2.1 帧与严格解析

v3 帧头为 `Magic(2B) || Ver(1B=0x03) || FrameType(1B) || BE32(Payload Length)`；帧类型与消息次序引用协议 §4.1。v3 首帧遇 `0x02`、`0x01` 或其他版本即关闭，不协商、不中途重试为旧版；另一端也必须检查每一握手帧的版本。混合版本部署只产生兼容性失败，不得解释为已获准降低保护级别。

签名所引用的 `descriptor_raw` **只能是该条 `CLIENT_AUTH_REQUEST` Payload 内 `device_descriptor` 字段的 length-delimited 嵌套 Protobuf 消息内容原始字节**：不含外层字段 key、嵌套字段长度 varint、帧头或帧 Payload 长度。客户端构造该字段时只序列化一次，并将完全相同的字节放入消息和签名转录；服务端从**收到的原始帧**定位该嵌套字段，提取内容和长度，先严格审计原消息，再以同一份经审计的字节验签和解析业务语义；不得解析后重序列化、规范化、修剪或选取另一个解析视图。客户端校验响应时也用自己实际发送并保留的这份原始字节构造服务端转录，不以服务端回显或重新编码代替。`BE32(descriptor_raw_len)` 是无符号 4B 大端长度，长度恰等于所提取字节数；受 16KiB 握手帧上限约束。

v3 接收侧须对 `ClientHello`、`ServerChallenge`、`ClientAuthRequest`、嵌套 `DeviceDescriptor`、`ServerAuthResponse` 以及挂起阶段消息执行同一严谨 wire 检查：拒绝已知字段重复（尤其随机数、长期/临时公钥、嵌套 descriptor、签名、`status`、`reason_code`、挂起 token/nonce/seq）、未知字段、错误 wire type、非最短 varint（字段 key、长度、整数值）、非法长度、无法完整消费的字节及非法 UTF-8；拒绝不合法枚举值，不能依赖不同 Protobuf 实现的“最后字段获胜”、未知字段忽略或重新序列化决定签名对象。已知 proto3 标量缺省值若字段缺失，语义严格按零解释；不得一端将缺省视为另一状态，特别是缺失的 `status`/`reason_code` 须按零进入下述组合约束。随机数、两方必要公钥、descriptor 和签名等必需 bytes/消息字段须各恰有一项并符合长度；descriptor 内现有四个 string 字段允许按 proto3 缺省语义为空，但如出现则各至多一次。严格检查通过前不能创建准入记录、解释拒绝原因或交付业务；坏帧直接断开。v3 禁止所有未知握手字段是刻意选择的版本内扩展边界，今后扩展须另审版本策略。

### 2.2 域分离及两个精确签名输入

`||` 表示字节原样连续拼接；除明确的 `BE32` 外不添加隐含前缀、分隔符或填充。域分隔末尾 `0x00` 是单个零字节，随后是单字节版本 `0x03`；域 ASCII 不含引号。

```text
ClientSignInput = ASCII("rsetup-next/client-auth/v3") || 0x00 || 0x03
  || client_random(32) || server_random(32)
  || client_ed25519_pub(32) || client_x25519_eph_pub(32)
  || BE32(descriptor_raw_len) || descriptor_raw

ServerSignInput = ASCII("rsetup-next/server-auth/v3") || 0x00 || 0x03
  || server_random(32) || client_random(32)
  || client_ed25519_pub(32) || client_x25519_eph_pub(32)
  || BE32(descriptor_raw_len) || descriptor_raw
  || server_x25519_eph_pub(32) || status(1B) || BE32(reason_code)
```

板端使用其 Ed25519 长期私钥签 `ClientSignInput`；中控使用其 Ed25519 长期私钥签 `ServerSignInput`；板端只接受其可信中控公钥列表中的有效签名（协议 §4 前置签名要求）。服务端先检查完整且无歧义的请求，验证板端签名，再查询准入；客户端先验证完整且无歧义的最终响应及中控签名，再根据已认证的 `status/reason_code` 行动。服务端转录包括请求中的板端长期公钥与原始 descriptor、两方随机数及双方临时公钥、状态和原因；客户端转录也显式绑定自己的长期公钥。对 `status` 编码为恰一字节 `0` 或 `1`，`reason_code` 是语义 uint32 的恰四字节大端；它们**不是** Protobuf 的 wire varint 原字节。签名可验证不代表准入批准：`APPROVED` 仍受当前权威准入与连接代际复查约束（协议 §4.5–4.6）。

`ServerAuthResponse` 的允许组合：`APPROVED(status=0)` 必须 `reason_code=0`，`server_x25519_eph_pub` 恰 32B 且满足 §4.4 的有效临时公钥/非零共享密钥约束；`REJECTED(status=1)` 必须恰 32B 全零占位临时公钥，原因仅限协议 §4.2 既有枚举中本流程可以合法发出的 `0=UNSPECIFIED`、`2=REVOKED`、`3=APPROVAL_DENIED`、`4=HANDSHAKE_TIMEOUT`（仅相应握手步骤）、`5=SERVER_ERROR`。保留枚举 `1=SIGNATURE_INVALID` 的定义以供版本演进时审议，**v3 对非法签名不发送这个值，也不将其当作可发出的 REJECTED 原因**；其他值及状态/原因/公钥非法组合一律拒绝并断开。`REVOKED`/`APPROVAL_DENIED` 只有在可信签名、合法组合验证后才可使板端停止自动重连并置本地未授权（协议 §4.6）；过载使用签名 `SERVER_ERROR` 而非永久拒绝。

### 2.3 验签失败及准入时序

```text
Client -- TCP / CLIENT_HELLO(v3) --> Server
Client <-- SERVER_CHALLENGE(v3) -- Server
Client -- CLIENT_AUTH_REQUEST(v3, client signature) --> Server
            Server 严格解析、验签；失败：立即关闭 TCP，绝不回复拒绝帧，
            不写永久准入决定，不启用 h2c。
            成功：按现有准入快照、资源配额、审批 PENDING/probe、最新代际复查。
Client <-- 完整认证上下文下的已签 SERVER_AUTH_RESPONSE(v3) -- Server
            （APPROVED；或合法 REJECTED + 已签 reason_code；
              首个 PENDING 与 ping-pong 若需要，仍在最终响应之前。）
            Client 严格解析、验中控签名；失败：立即关闭 TCP，
            不信任伪造原因，不设永久未授权，不启用 h2c。
            仅双方认证有效且 APPROVED：X25519/HKDF、记录层、同 socket h2c。
```

请求在拥有完整认证上下文之前就超时、畸形或被资源门拒绝时直接关闭；**有完整且已通过签名验证的认证上下文**时，其余可归类拒绝须发受中控签名保护的最终响应，包含准入拒绝、可重试资源错误以及适用的握手步骤超时（仅当连接仍可发送且该原因适用）。如果无法产生可信签名或 TCP 已失效，就关闭而不伪造已签响应；不以“需要拒绝响应”为由延长协议期限。验签失败事件可记审计/计数与限速依据，但不能单凭该事件写入 REVOKED、APPROVAL_DENIED 或板端本地永久未授权。PENDING 明文 probe 仍不能代替最终签名；时序中本项替换现行协议 §4.5 图中“签名失败 → REJECTED(reason_code=1)”分支，而不是声称现行图已改变。

## 3. 记录层致命错误与恢复边界

成功握手后仍按协议 §5.1 使用 `SharedSecret=X25519(...)`、`Salt=client_random||server_random`、HKDF-SHA256 Extract/Expand，`info` 逐字为 `rsetup-next/tunnel/c2s-key`、`rsetup-next/tunnel/s2c-key`、`rsetup-next/tunnel/c2s-iv`、`rsetup-next/tunnel/s2c-iv`，分别派生 32/32/12/12B。按 §5.2 保留 `Record Length=BE32(ciphertext+16B tag)`、`Nonce=IV_Base[0:4]||(IV_Base[4:12] XOR BE64(SeqID))`、`AAD=BE32(Record Length)||BE64(SeqID)`；两方向密钥/IV 与 `TxSeq`、`RcvSeq` 独立，初始序号均为零。拟将接收有效长度收紧写明为 **16≤Record Length≤65536**（均含 tag，允许零字节明文的 16B tag 记录），不得先按不可信长度无界分配。

收到长度 `<16`、`>65536`、长度字段或记录体截断/有界读取超时、tag 或 AAD 校验失败、期望序号耗尽，或者发送端发生记录的部分写入/无法确认整条记录完整写出时，**立即终止整条 TCP**，使该连接的密钥、两个方向序号、缓冲与 h2c 状态失效；不能仅丢一帧、仅关一条 gRPC 流、同连接补发或扫描下一个可能的帧头重同步。任何密文须在**整条记录**的长度/完整性/AAD/tag 校验通过前都不向 h2c/业务交付明文；失败不增加 `RcvSeq`，但也绝不在原连接继续尝试接收下一记录。发送端在每个方向串行化记录加密与发送，不得以同一 `TxSeq` 并行加密多条记录；只允许在一条记录完整成功发出后按记录推进 `TxSeq`；部分写入后的 TCP 无条件销毁，不允许重用相同 key/nonce。序号按检查加法处理：拟允许发送/接收序号 `0..2^64-2`，在需要使用 `2^64-1` 或任何可能回绕之前以耗尽错误关闭；该保守边界防止 wrap，不把异常重置为零。

关闭后按协议 §7 的指数退避 `1s,2s,4s,…≤60s` 加 `[0,1s)` 均匀抖动，再以**新 TCP、新完整 v3 握手、新随机数和新临时密钥**连接，不复用旧 key/IV/序号或 PENDING token；按 §6.6 结清旧连接代际的未决请求。网络失败可能发生在对端已解密并执行设备变更/重启之后：不自动重放潜在有副作用操作，应按任务持久记录与状态查询核实（中控设计 §13；计划 02 Task 7–10）。攻击者可通过断连造成 DoS，本策略不承诺避免 DoS；仍需协议 §4.6 的未认证/挂起连接配额、来源与全局握手限速，以及退避抖动。记录部分帧的**具体有界读取 deadline** 是发布前专家审定事项；无论选定多少，超时都必须走上述致命关闭，而不能无限挂起。

## 4. 从 `0x02` 到 `0x03` 的部署与拒绝边界

- v3 端只发/只收 v3 握手帧；v2 端现有定义只认 v2，不能假设它会理解新转录或原因签名。任一侧遇不匹配版本立即关闭；不得在相同或新 TCP 上因失败自动尝试 v2，不得跨版本借用握手、密钥、签名、审批结果或记录状态。留存 v2 连接不能成为 v3 安全证明。
- 双端需协调升级窗口、可信中控公钥与板端配置、旧连接清理及回滚条件；先升级哪一端、混合版本停机预算和拒绝回退的实际部署顺序仍待专家/运维评审。若无法保证双方升级，选择暂不启用 v3 隧道，而不是临时放宽验证。
- 现在**不得**仅依据本稿修改 `docs/protocol_spec.md`、计划 02 的 `SE/v2` 示例或 Task 3/4 暂定测试体；用户复审本文并完成独立审查后才统一修原文、计划和双端测试。当前协议仍是 v2，且计划的安全关卡未解除。

## 6. 剩余独立审查决策与发布关卡

以下是**需要批准的开放决策**，不因本文写出拟议方向就自动获批：

1. 客户端签名转录是否仍需显式绑定握手 `FrameType`，以及是否对服务端转录作对称处理？当前第 2.2 节**没有**擅自新增该字节；须先对跨角色/跨帧复用威胁进行专家审查，若批准新增字节须修订转录和所有向量，并再明确版本边界。
2. 记录部分帧、发送堵塞与整帧读取使用何种有界单调时钟 deadline、缓冲预算、背压与慢速攻击防护；这不改变任何错误终止 TCP 的已确认方向。序号末值保守保留策略及零明文记录的互操作细节亦须随向量审阅。
3. 真实 wire 字节、签名、HKDF、Nonce/AAD、tag 的**固定数值向量**由谁独立生成和复核；不同语言/Protobuf 库如何证明原始字段提取、缺省标量与重复/未知字段拒绝一致。本文没有虚构向量或密码审计结论。
4. v2 老端、v3 新端的分批升级顺序、停机窗口、回滚约束与无法协同升级时的拒绝服务影响；不可将临时启用 v2 回退作为解决办法。
